# Sprint 2/3 conventions: GitHub and Cloudflare

This document explains how we work together during the Iris and Atlas sprints. Both squads follow the same rules, so when the two sprints merge back together, things just work.

## GitHub side

### Branch model

```
main                    release, protected
└── dev                 integration, both sprints land here eventually
    ├── dev-iris         Iris squad's integration branch
    │   ├── iris-01-...  per-ticket branches
    │   └── iris-02-...
    └── dev-atlas        Atlas squad's integration branch
        ├── atlas-01-...
        └── atlas-02-...
```

Each ticket gets its own branch, and that branch comes off the engine's own integration branch (`dev-iris` or `dev-atlas`), never off `dev` directly. With two squads working at the same time, we don't want half-finished work from one engine landing in `dev` in between pieces of the other engine's work. Each engine collects its own finished tickets first, and only a working set goes into `dev`.

Before merging an integration branch into `dev`, rehearse it first: `git merge-tree dev dev-iris` (or `dev-atlas`) shows what the merge would look like without changing anything. This catches problems before they happen instead of after.

Branch protection on `main` is turned on from day one: no direct pushes, a pull request is required.

### Pull requests and review

- Each engine is reviewed by its own reviewer. Reviewers do not cross-review the other engine's work.
- Every pull request has exactly one named owner responsible for delivering it.
- Keep changes small, roughly under 400 lines, and split by ticket rather than by convenience. A change that is too big to review carefully will be reviewed carelessly instead.
- Tick the ticket's checkboxes in the same change that does the work. Leaving it for later means it doesn't happen.

### Lockfile rule

Never fix a `package-lock.json` conflict by hand. If there's a conflict, delete the file, reinstall, and commit the fresh one. Lockfiles are generated by the tools and are not meant to be edited or merged by a person.

### CI

A GitHub Actions workflow runs on every pull request into `dev-iris`, `dev-atlas`, and `dev`. It does three things:

1. A clean install (`npm ci`).
2. Type checking (`npx tsc --noEmit`) for each part of the codebase that changed.
3. Running the tests (`npm test --workspaces --if-present`).

CI never makes real model calls, so it never spends money and never needs network access. Any test that touches the `AI` binding or the AI Gateway must fake it instead.

## Cloudflare side

This section describes the pattern every engine's Cloudflare setup follows, based on how `apps/agent-helios` is already built.

Each of `apps/agent-iris` and `apps/agent-atlas` gets its own, separate copy of each of these, with one exception (R2, below):

| Resource | What it's for and how it's set up | Reference |
|---|---|---|
| Durable Object | Its own class (`IrisAgent`, `AtlasAgent`), with a `new_sqlite_classes` migration, and a binding name that matches the class name | `wrangler.jsonc:10-24` |
| D1 database | Its own database, with its own `migrations_dir` under `infrastructure/d1/migrations/<engine>/` (not shared with Helios's) | `wrangler.jsonc:39-46` |
| R2 bucket | **Shared, not separate.** Iris and Atlas both bind `PATTERNS` to the same bucket, `images-bucket`. R2 has no migrations and no schema, so sharing it carries none of the risk that keeps D1 separate. Each engine writes under its own key prefix, `iris/{p_invoc_id}.jpg` and `atlas/{p_invoc_id}.jpg`, so there is no collision even though the bucket is one. Helios keeps its own separate bucket; this sprint does not touch Helios | `wrangler.jsonc:31-37` |
| KV namespace | Its own namespace. The binding name stays exactly `CONFIG` for every engine, so the worker code looks identical everywhere; each engine is told apart only by its dashboard title (`IRIS_CONFIG`, `ATLAS_CONFIG`). No `preview_id`, so there is only one store per engine, matching what production actually reads | ADR-0008 |
| `AI_GATEWAY_ID` | Its own gateway id, set as a plain `var`, never in KV. If this value is blank or misspelled, calls silently fall through to Workers AI directly with no logging, so it needs to stay somewhere a person reviews it | `wrangler.jsonc:85-91`, ADR-0006 |
| `ALLOWED_ORIGINS` | Its own list of allowed website origins for CORS, set as a plain `var`, never in KV, and never `*`. There is no login on the generate routes, and every call spends real money, so this list is what stops a random website from calling in and racking up a bill | `wrangler.jsonc:100-110` |
| Table prefix | Every database table this engine creates starts with `iris_` or `atlas_`. This avoids clashing with the Agents SDK's own internal tables, which live in the same database | ADR-0003 |

**Why D1 stays separate for now.** A single shared D1 with prefixed tables would make cross-engine queries easier, but applying a migration against a shared, live database can't be rehearsed the way a branch merge can. Two squads both adding tables to one database during active parallel work is exactly the kind of shared, mutable resource to avoid. Each engine keeps its own database for the length of the sprint.

**Consolidation happens once, at the end**, as its own joint ticket, after both squads' tables are stable and nobody is generating new migrations. At that point it becomes one deliberate, coordinated step instead of an ongoing coordination cost.

**To make that consolidation useful once it happens**, Iris's and Atlas's audit rows carry the upstream `p_invoc_id` forward as a plain column (Iris's row references the Helios run it colored, Atlas's row references the Iris run it repeated). This lets a person stitch together a full-pipeline view today from three separate queries, and it's what turns the eventual single-database join into three tables that actually tell one connected story, rather than three tables that just happen to share a database.

**App naming**: `apps/agent-iris` and `apps/agent-atlas`, matching the pattern `apps/agent-helios` already uses.

**Folder structure inside each app**: copy the Helios Structure. `index.ts` only handles routing. `agent.ts` is the Durable Object itself and acts as its own controller. `config.ts` is the only file allowed to read from KV. `services/` holds the orchestration logic and the actual model calls. `repository/` is the only place allowed to touch storage: DO SQLite, D1, and R2. `db/` defines the schema once and compiles it to both storage targets. `prompts/` holds any hand-written prompt text, versioned, if the engine calls a text or image model that needs one.

**Secrets.** Use `wrangler secret put` or `.dev.vars` for anything secret. Never put a secret in `wrangler.jsonc`'s `vars` section. Account identifiers and database IDs are fine to commit, they're just identifiers, not passwords. Anything that actually authenticates you to something is not fine to commit.

**Shared packages.** `packages/shared-types` and `packages/shared-utils` are now shared across all three engines. Both squads will read from these, and possibly add to them. This is the one place the two sprints could genuinely conflict, since everything else lives in its own separate `apps/` folder. Keep additions small, and have them reviewed by the other squad. Where possible, add a new exported item rather than changing the shape of something Helios still depends on.

**Not every Workers AI model takes the same kind of request, and this affects `shared-utils` directly.** `gpt-oss-120b` is text-only, no image input. `flux-1-schnell` (Helios's image model) is text-to-image only, also no image input. Models that accept an input image, like `flux-2-klein-4b`/`9b`, use a different request shape: multipart form data, not the plain JSON body `getTextualModelOutput` and `getImageModelOutput` currently assume. Any engine that needs to send a model an existing image needs either a new shared helper for this multipart shape or a clear extension of an existing one. Build it once, in `shared-utils`, reviewed by the other squad.

**Runtime config values are read once per request, never once at Durable Object wake-up and never cached at module level** (ADR-0008). This carries over unchanged to Iris's and Atlas's own `config.ts` files.

**Retry logic is decided per stage, based on how that specific model call actually fails.** It is not just copied from Helios without thinking about it (ADR-0009). Whether a call needs an automatic retry depends on whether it tends to fail in a recoverable way (a structured output request coming back slightly wrong, cheap to just ask again) or in an unrecoverable way (an expensive, one-shot call likely to fail the same way again). Each engine decides this explicitly for itself, including whether to build more complete retry logic for an unusual or empty model response, and whether to use the AI Gateway's own built-in retry instead of writing our own.

## Team

The team works as one shared pool across both engines, not two fixed, separate squads. Every ticket still gets exactly one named owner and one named reviewer. Ownership is about who is accountable for a piece of work, not about restricting who is allowed to touch it. The same person can pick up tickets from both the `iris-*` and `atlas-*` backlogs.

Unassigned work is marked **unassigned, needs roster** rather than left blank, so nothing is silently forgotten.
