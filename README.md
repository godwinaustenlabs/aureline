# Aureline — Autonomous Textile Design Intelligence Platform

## 1. What this project is

Aureline is an AI platform that turns a textile design concept (a text description like "woven jacquard with a damask pattern in muted gold") into a production-ready design. The current build phase covers exactly one deployable component: **agent-helios**, a Cloudflare Worker that runs a two-model pipeline — a high-creativity text/planner model that distills a design concept into structured parameters (color, contrast, tone, style, composition), and a low-creativity image model that renders those parameters faithfully.

Everything beyond Helios (orchestration, API gateway) is intentionally deferred and documented below.

## 3. apps/agent-helios

**What it does.** Accepts an HTTP request and, in the future, runs the two-model pipeline. Today the pipeline logic is a stub: `onRequest` returns a fixed string.

**How Agents SDK / Durable Objects works here.** Cloudflare's `agents` library (v0.19.0) wraps Durable Objects so each agent instance is a Durable Object with SQLite storage, HTTP routing, and WebSocket support built in. The worker's `fetch` handler delegates to `routeAgentRequest`, which inspects the URL path — requests under `/agents/<AgentName>/<instance-id>` are forwarded to the matching Durable Object's `onRequest` method. Everything else falls through to a 404.

**What's implemented vs. stubbed.**

| Artifact | Status |
|---|---|
| `HeliosAgent` class (extends `Agent<Env>`) | Stub — `onRequest` returns a static string |
| `MyDurableObject` class (extends `DurableObject<Env>`) | Stub — `sayHello` RPC method exists but is unused |
| Two-model pipeline (text-planner + image model) | Not started |
| Integration with any AI model API | Not started |

**wrangler.jsonc bindings** (actual contents):

```jsonc
{
  "name": "agent-helios",
  "main": "src/index.ts",
  "compatibility_date": "2026-07-27",
  "migrations": [
    {
      "new_sqlite_classes": ["HeliosAgent"],
      "tag": "v1"
    }
  ],
  "durable_objects": {
    "bindings": [
      {
        "class_name": "HeliosAgent",
        "name": "HeliosAgent"
      }
    ]
  },
  "observability": { "enabled": true },
  "upload_source_maps": true,
  "compatibility_flags": ["nodejs_compat"]
}
```

- `durable_objects.bindings[0]` maps the JS class `HeliosAgent` to a binding named `HeliosAgent` so the worker can look up and call agent instances by name.
- `migrations[0]` tells Cloudflare to create SQLite storage for the `HeliosAgent` class when first deployed.
- `nodejs_compat` enables Node.js API shims (`Buffer`, `process`, etc.) inside the Workers runtime.
- `MyDurableObject` was generated by the `create cloudflare` starter but is **not** registered in `wrangler.jsonc` — it has no binding. It exists in source but is unreachable at runtime. This is leftover scaffolding that should be removed before production.

**Shared dependency.** `agent-helios` depends on `@aureline/shared-types` via workspace symlink. The actual interface it will use is already defined (see §4).

## 4. packages/

Two packages exist. Both are declared in the root `package.json` workspaces and are resolved as symlinks under `node_modules/@aureline/*`.

### `@aureline/shared-types`

Defines the contract between Helios and its eventual callers. Single source of truth so the API gateway (future), Athena (future), and Helios all agree on request/response shapes.

```ts
// packages/shared-types/src/v1/messages.ts
export interface HeliosRequest {
  concept: string;
  requestId: string;
}

export interface HeliosParams {
  color: string;
  contrast: string;
  tone: string;
  style: string;
  composition: string;
}

export interface HeliosResult {
  requestId: string;
  imageUrl: string;
  params: HeliosParams;
  modelVersion: string;
  cost: number;
}
```

The pipeline flow these types describe: `HeliosRequest` → (text-planner) → `HeliosParams` → (image model) → `HeliosResult`.

### `@aureline/shared-utils`

Placeholder. `package.json` exists but `"main": ""` and no source files except `src/.gitkeep`. Intended for utility functions (e.g., prompt templates, cost calculation) that multiple apps would import.

### Why shared rather than duplicated per-app

Workspace packages are symlinked at install time. A change to `shared-types` is instantly visible to every app that depends on it, without any publish step. When Helios is the only consumer there's little benefit, but once api-gateway or Athena arrives, duplicating these interfaces across apps would create drift.

## 5. tests/

The root `package.json` sets `"directories": { "test": "tests" }`, which reserves `tests/` for the project. Today it contains only `.gitkeep`.

There is no test runner configured. The `test` script in root `package.json` is `echo "Error: no test specified" && exit 1`.

When AI-evaluation material is added (test prompts, scorecards, expected outputs for tuning Helios's models), it should live in `tests/evals/` to keep it distinct from unit/integration tests. Evals are qualitative — they measure whether the model output is good, not whether the code is correct — and usually involve manual review or batch scoring rather than `assert` statements.

## 6. Deployment model

Each folder under `apps/` is a standalone Cloudflare Workers project with its own `wrangler.jsonc`. Cloudflare's Git integration (Workers & Pages → your repo → "build watch paths") can be configured so that:

- A push changing `apps/agent-helios/**` triggers a deploy of **only** `agent-helios`.
- A push changing `packages/shared-types/**` triggers a deploy of **every** app whose watch path includes that package.

Today there is exactly **one** app (`agent-helios`), so there isn't a meaningful distinction yet. The pattern matters once a second app appears.

No CI workflows (`.github/workflows/`) exist yet. Deployments must be run manually with `npm run deploy` inside the app directory, which calls `wrangler deploy`.

## 7. Deliberately not here yet

### api-gateway

An HTTP gateway that authenticates requests, rate-limits, and routes them to the correct agent. It is not built because there is nothing to route — Helios is the only agent, and directly exposing `wrangler dev` on port 8787 is sufficient. The api-gateway will be built as a separate app under `apps/api-gateway` as soon as there is a second consumer of Helios (a web UI, an integration partner, etc.) that justifies the indirection.

### agent-orchestrator (Athena)

An orchestrator agent that decomposes complex design briefs into sub-tasks and delegates them to specialist agents (Helios for rendering, others for color-matching, material selection, etc.). It is not built because there are no specialist agents to orchestrate. Work on Athena will start once Helios's two-model pipeline is producing reliable results and there is a concrete need to chain agents together.

## 8. How to run it locally

### Prerequisites

- Node.js ≥ 18 (for `wrangler`)
- A Cloudflare account (for `wrangler deploy` — not needed for local dev)

### Commands

```bash
# Install all workspace dependencies from the repo root
npm install

# Start the agent-helios dev server (defaults to port 8787)
npm run dev --workspace=apps/agent-helios

# Or, from inside apps/agent-helios:
cd apps/agent-helios
npm run dev

# Open http://localhost:8787/ — returns "Helios agent running"
```

The `dev` script calls `wrangler dev`, which compiles TypeScript on the fly, starts Miniflare (the local Cloudflare Workers simulator), and watches for file changes.

### Available scripts per app

```
deploy   → wrangler deploy          # Push to Cloudflare Workers
dev      → wrangler dev             # Local dev server with live reload
start    → wrangler dev             # Alias for dev
cf-typegen → wrangler types         # Regenerate worker-configuration.d.ts after binding changes
```
