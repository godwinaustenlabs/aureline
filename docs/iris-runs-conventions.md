# Reading `iris_runs`

What Iris's audit table means, for anyone writing a query against it who did not build it. The decisions behind these rules are in ADR-0001, ADR-0005, ADR-0008 and ADR-0010; this is the reader's guide. The identifier model it depends on is in [AGENTS.md](../AGENTS.md) §3.

The same schema is used twice. The Durable Object holds a session's recent runs and is pruned; D1 holds the permanent copy and is not. One schema, two migration outputs, generated by `db:generate` and `db:generate:d1`.

## The two ids, which are not the same thing

This is the part most worth reading before writing a query, because both columns are UUID-shaped strings and picking the wrong one gives an answer that looks plausible and is wrong.

**`pipeline_id` is one run of Iris.** Minted per invocation in `services/pipeline.ts`. Re-running the same design produces a different one. It is **not** a Durable Object identifier: one DO accumulates many invocations, and the DO is chosen by `session_id`, which never appears in this table.

**`design_session_id` is the design.** Minted once upstream and carried unchanged through every engine, so Helios's pattern, Iris's colouring of it and Atlas's placement of that all answer to the same value. It is required on every request and every row.

So:

| Question | Column to group or filter by |
|---|---|
| What did this one run of Iris do? | `pipeline_id` |
| Every attempt Iris made at this design | `design_session_id` |
| The latest attempt at this design | `design_session_id`, then newest `created_at` |
| What did this whole design cost across engines? | `design_session_id`, once the databases are merged |

The last one is not a join yet. Each engine has its own D1 database this sprint, so a full-pipeline view means three queries filtered on the same `design_session_id` until the consolidation ticket merges them. Carrying the column now is what makes that eventual join possible.

**Helios is not renamed yet.** It still calls its pipeline id `p_invoc_id`. A caller bridging the two has to supply Iris's `design_session_id` itself; Iris will not accept the old `source_p_invoc_id` field name and will not mint one.

## One invocation is always two rows

Every `POST /generate` produces exactly two rows sharing a `pipeline_id`: one `modality: "text"` and one `modality: "image"`. This holds **whether the invocation succeeded or failed** (ADR-0001), including when it failed before the planner ran — `insertFailedImageRun` exists precisely so a failure still leaves a pair.

That matters for more than tidiness. `pruneCompletedRuns` deletes whole runs whose rows are *all* `completed`, so a failure that left a lone `completed`-looking text row would be pruned like a success and the record lost.

The image row duplicates `planner_params` and `motif_ref` from its text sibling rather than requiring a join, so a failed image is inspectable on its own.

## Status, and which combinations are legal

`running` exists only mid-invocation. The pipeline is synchronous, so an HTTP response always carries a settled status; a `running` row in D1 would be a bug, and `getSettledRows` exists to make sure one never gets exported (ADR-0010).

| text | image | what it is |
|---|---|---|
| `running` | absent | in flight, before the planner returned |
| `failed` | `failed` | the planner or its validation failed. Nothing to resume |
| `completed` | `running` | in flight, image being made |
| `completed` | `completed` | success |
| `completed` | `failed` | the image failed. **This is what `POST /resume` will recover** (iris-10) |

Anything else is a bug worth reporting — in particular a `failed` text row next to a `completed` image row, or any invocation with one row.

## Columns

**`user_prompt`** is the caller's `concept`, copied onto both rows. The request calls it `concept` and the column calls it `user_prompt`; they are the same string. The names differ for historical reasons and the column name is the one every query uses.

**`motif_ref`** is the reference to the pattern Iris coloured — an R2 key or a URL, never image bytes.

**`planner_params`** is the validated `IrisParams` object. `{}` on a row whose run never got past the planner. Read it back through `IrisParamsSchema` rather than trusting it: it is a JSON column typed `unknown`, and a row written under an older colour vocabulary must fail loudly rather than produce a nonsense image.

**`image_r2_key`** is set on a successful image row only, always `iris/{pipeline_id}.jpg`. Keyed by pipeline id and not design session id, so a re-run never overwrites the image the previous attempt produced. The bucket is shared with Atlas and separated by prefix, not by bucket.

**`cost_usd`** is null throughout while the planner and colorizer are fakes (iris-05). iris-08 and iris-09 fill it from the AI Gateway log. Do not sum this column and conclude Iris is free.

**`completed_at`** is set when a row settles, on both success and failure.

**`model_metadata`** is free-form JSON, and is the **only durable home for the image's `width` and `height`** — there is no column for them and deliberately never will be (iris-03 decision 9). It also carries the model actually called, and, once iris-10 lands, a resume's `root`, `resumed_from` and `attempt` markers. `countResumeAttempts` reads `root` out of it, which is how the cap on spend per concept is enforced.

## Things that will surprise you

**Failed runs are never pruned.** Only runs whose every row is `completed` are eligible, so a session that fails a lot grows without bound in the DO. That is deliberate: the failures are what someone came looking for.

**`listRuns` includes `running` rows and `getSettledRows` does not.** The first is for a human watching a session and wants in-flight work visible; the second feeds the exporter, where a half-written row would freeze null params and a null cost into D1 permanently.

**The DO holds recent runs, not all runs.** Anything asking "what has this session ever done" must read D1, not the Durable Object.
