# Retry policy is decided per stage, and the image stage's retry is a person

Ticket 08 asked for "automatic retry on failure", which reads as one policy for the whole pipeline. Building it that way would have been wrong, and the reason is not in the code anywhere, so it is written down here.

The two model calls fail in shapes that have nothing in common. The planner fails *recoverably*: it is asked for structured output, and what comes back is prose, or nearly-right JSON, or the right JSON with one enum value the schema does not accept. Asking again usually works, because the failure is the model wandering rather than the request being wrong, and each attempt costs about $0.001. The image model has no equivalent. A Flux call that failed, failed for a reason a second identical request will hit again, and each attempt is $0.0019, the expensive half of the invocation. An automatic retry there is a loop that spends real money on a request we have no reason to think will behave differently.

We considered a **pipeline-level retry** driven by a Workflows binding, a Queues binding, or a Durable Object alarm. Rejected. Every one of them re-runs the planner as well, so the cheap half is paid twice to reach the expensive half that failed, and the re-run is a new invocation with a new `p_invoc_id` regardless, which means the retry machinery buys nothing that a second `POST /generate` does not already do. It also turns a synchronous request into an asynchronous one, which the wire contract is not written for.

We considered a **retry loop inside `generateImage`**, matching the one the planner already has. Rejected on cost. `config.maxRetries` exists on `HeliosConfig` and is deliberately *not* read there; the temptation to wire it up is exactly why this is an ADR rather than a comment.

**Decision:** retry policy belongs to the stage, not the pipeline. The text stage retries itself, inside `getTextualModelOutput`, governed by `max_retries` in KV. That loop is `for (attempt = 1; attempt <= maxRetries)`, so a configured 2 means two total attempts and not one plus two, and it catches both a schema mismatch and a thrown `ai.run`. The image stage never retries: `generateImage` calls `env.AI.run` exactly once. A failed invocation is never re-run automatically by anything.

The image stage's retry therefore is a person, and `POST /resume` is the mechanism. It reads the params the planner already produced and runs only the image half, so a retry costs $0.0019 rather than the $0.0029 a fresh request costs, and the caller gets back the same params they already saw. Because every attempt spends money, the decision to spend it is a human one, made once per attempt, rather than a number in a config file that multiplies the bill by itself.

A manual retry still needs a ceiling, and it does not get one for free. The guard on `POST /resume` refuses a run that already has an image, which stops the same success being paid for twice, but a run whose image genuinely failed can be resumed again and again, and every attempt spends the expensive model. "A person decides" is not a limit when the person can be a loop. So `max_resume_attempts` caps how many times one brief may be resumed, counted over the `root` the chain shares rather than over the `attempt` depth, because retrying the same failed run repeatedly produces siblings at equal depth and a depth cap would never fire. It sits in KV with the other config, and its schema caps it at 20 so a dashboard edit cannot authorise an unbounded bill either.

The consequence worth accepting: a transient image failure that a second immediate call would have survived now needs someone to notice and act. We prefer that to a config value that can quietly triple a bill, and the failed run is preserved and inspectable in the meantime, which is what makes the manual retry possible at all.
