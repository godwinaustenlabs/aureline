# Iris retries the planner and never the colorizer, and an unfetchable motif is refused rather than retried

ADR-0009 decided this question for Helios, and iris-10 could have cited it and stopped. It does not, because "the same conclusion" and "the same reasoning" are different claims, and only the second one is worth anything to whoever reads this next. What follows is the reasoning re-run against Iris's two calls, which happen to reach the same answer, plus three questions Iris has that Helios never had.

Iris's two stages fail in shapes that have nothing in common, which is the whole basis of a per-stage policy. The planner is asked for structured output and comes back wrong in recoverable ways: prose instead of JSON, nearly-right JSON, a colour name outside `ColorNameSchema`'s vocabulary. Asking again usually works, because the failure is the model wandering rather than the request being malformed, and an attempt is about $0.001. The colorizer has no equivalent. It is an image-to-image call that already succeeded at being well-formed by the time it fails, so a second identical request hits the same reason, and iris-06 measured it at roughly $0.017 per call, the expensive half of the invocation by an order of magnitude rather than the two-thirds it is in Helios. The gap between the two stages is wider here than it is there, so if the per-stage split is right anywhere it is right here.

**Decision:** the text stage retries itself and the image stage never does. `services/planner.ts` passes `config.maxRetries` into the shared `getTextualModelOutput`, whose loop is `for (attempt = 1; attempt <= maxRetries)` and catches both a schema mismatch and a thrown `ai.run`, so a configured 2 is two attempts in total and not one plus two. `services/colorizer.ts` calls `env.AI.run` exactly once and holds no retry of its own. Nothing re-runs a failed invocation automatically. The image stage's retry is a person, and `POST /resume` is how they express it: it reads the params already on disk and runs only the image half, so a retry costs the image call rather than the image call plus the planner, and it is capped by `max_resume_attempts` counted over the chain's `root`. `runImageStage` is exported separately from `runPipeline` for exactly this re-entry.

**A well-formed response that is empty or nonsense is a real failure, not a retry.** The planner can return valid JSON, valid enum members, and params nobody would want. It passes `IrisParamsSchema` and reaches the colorizer, which spends real money colouring a motif to a palette that does not answer the brief. The tempting fix is a plausibility check that re-enters the retry loop. We are not building one, and the reason is that "nonsense" has no machine-checkable definition. Any check we wrote would be a proxy for taste, it would reject good params about as often as bad ones, and a retry loop whose exit condition is a judgement call is a loop we cannot bound. That is the same objection ADR-0009 raised against a retry inside `generateImage`, arriving from the semantic side instead of the cost side. If it parses, we accept it, the run completes, and the caller decides whether to spend again. A bad but valid result is visible to the person who asked for it in a way a silently swallowed retry never is.

**We are not using the AI Gateway's built-in retry.** Two reasons, written down because this question has already returned twice. The gateway retries at the transport layer: it sees a status code and a timeout, and it cannot see that a 200 came back carrying JSON our schema rejects. Schema failure is the only thing our text retry exists for, so the gateway's retry would not replace it, it would sit underneath it and retry a different class of problem. Worse on the other stage: a gateway retry applies per request, so it would silently re-issue the exact image call ADR-0009 and this ADR both refuse to re-issue automatically, and the second charge would appear in the gateway log with nothing in our own rows to explain it. Note honestly that this is currently theoretical. `AI_GATEWAY_ID` is `"iris"` in `wrangler.jsonc` but no gateway id is passed at the call site, so `buildAiRunOptions` returns `undefined` and no gateway options are in effect at all today. The answer does not change when the id is wired; it becomes enforceable rather than moot.

**An unfetchable motif is refused, not retried.** This is the failure Iris has and Helios does not, and it is the one most likely to actually happen, because the motif is another engine's output living in another engine's storage. It could plausibly be called transient and given a bounded fetch retry. We are refusing instead. `readMotif` throws on a missing key, a non-2xx over HTTP, and a zero-byte object, and it runs before the model in every path, so the check is already free wherever it happens. A missing motif is very rarely a network blip and very often a key that was never written, was written to the other bucket, or was pruned, and none of those get better on a second attempt. `POST /resume` therefore reads the motif before it opens a row and refuses with a 409 naming the ref, rather than opening two rows and settling them `failed`. A refusal never became an invocation, so there is nothing to record and nothing was billed; returning a `failed` result would claim a run happened.

**`root` and `design_session_id` answer different questions and both stay.** They overlap enough to be confused and the confusion would be expensive, so: `design_session_id` is minted upstream, travels unchanged through every engine, and answers "everything that went into this design". `root` is minted by Iris, spans only the retries of one brief inside Iris, and answers "what has this one attempt cost so far". One design session can hold several unrelated briefs, so they are not interchangeable in either direction. The spend cap counts `root` and must never count `design_session_id`: capping the design session would refuse a brief that has never been retried because a different brief in the same session was, and it would also be unbounded in the other direction the moment a caller reused a session id. `countResumeAttempts` reads `root` out of `model_metadata` for this reason.

The consequence worth accepting is the same one Helios accepted: a transient image failure that an immediate retry would have survived now needs a human to notice and act. We prefer that to a config value that can quietly multiply a bill, and the failed run is preserved and inspectable in the meantime, which is what makes the manual retry possible at all.
