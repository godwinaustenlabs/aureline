# Runtime config is resolved from KV per invocation, with wrangler vars as the committed fallback

Helios' tunable values lived in `apps/agent-helios/wrangler.jsonc` `vars`: `PLANNER_MODEL`, `IMAGE_MODEL`, `MAX_RETRIES`, `RETENTION_LIMIT`. `vars` are baked in at deploy time, so changing the planner model or the retry count meant redeploying the whole Worker. For a repo that is the template for six more engines, that is the wrong default. Model choice, retry count and retention limit are policy, not code, and the people who will want to change them are not always the people who can deploy.

Decision: four values are read from the `CONFIG` KV namespace at runtime — `text_model`, `image_model`, `max_retries`, `retention_limit`. KV holds the live value and is **edited by hand from the Cloudflare dashboard**; the app only reads it. There is no write path, no config API and no admin token. The matching `vars` stay in `wrangler.jsonc` as the committed, reviewed fallback for when a key is absent or its value is invalid. `src/config.ts` owns the mapping between the two, and it is the only file that has to change when a value moves between them.

`AI_GATEWAY_ID` is deliberately excluded. `buildAiRunOptions` (`packages/shared-utils/src/aiGateway.ts`) returns `undefined` when the gateway id is empty, which sends the call straight to Workers AI with no error, no gateway log entry and no request metadata. A blank or misspelled value typed into a dashboard would therefore be a silent routing outage, visible only as the `aiGatewayLogId` warning in `planner.ts`. It stays in `wrangler.jsonc`, where changing it goes through review. The same reasoning would apply to anything else whose wrong value degrades quietly rather than failing.

`MAX_OUTPUT_TOKENS`, the image cache TTL and the Flux sampling inputs stay hardcoded in `packages/shared-utils` for now. They are model-tuning knobs rather than policy, and none of them has a second consumer yet. Moving them later is the same three edits this ADR describes.

The read happens once, at the top of `runPipeline`, and the resolved `HeliosConfig` is threaded to every stage as a plain object. Two alternatives were rejected. Reading in `onStart()` looked cheaper, but `onStart` runs once per **Durable Object wake-up** and a DO can stay alive for hours, so the config would freeze for the life of the instance and dashboard edits would appear to do nothing — the most confusing possible failure. Reading per service was rejected because four independent reads inside one request can straddle a KV edit and disagree, producing a `helios_runs` row that records one model in its metadata and another in its parameters. That is exactly the lying audit row ADR-0001 exists to prevent. One read per invocation gives every stage the same snapshot.

Reads are a single bulk `get` with an array of keys and `cacheTtl: 60`, which caps edge reads at roughly one per key per minute per colo. 60 seconds is already the propagation floor for KV writes, so a shorter TTL buys nothing. The result is deliberately **not** cached in a module-level variable: module scope in a Durable Object survives across invocations, which would reintroduce the `onStart` freeze through the back door. The `cacheTtl` is the cache.

Nothing in the resolver throws. A missing key, a value that fails validation, and KV itself being unavailable all fall back to the matching var and `console.warn`. A typo in a dashboard field must not be able to take the service down, and `resolveConfig` runs outside `runPipeline`'s try block, so a throw there would escape as an opaque 500 rather than a settled `HeliosResult`. Each KV value is validated with Zod before it is accepted — models as non-empty trimmed strings, `max_retries` as an integer 1 to 5, `retention_limit` as an integer 1 to 100. The vars are not re-validated; they are reviewed in the repo. A numeric var that is somehow missing falls to a last-resort constant that mirrors `wrangler.jsonc`, and warns that `wrangler.jsonc` is broken.

Failing loudly instead was considered and rejected for the same reason: the whole point of moving these values to a dashboard is that a non-deploying person can change them, and that person needs a wrong value to be recoverable, not fatal. The cost of this choice is that a bad edit is quiet, so `resolveConfig` also returns a per-field `source` map (`"kv"` or `"var"`) and `runPipeline` logs one line per invocation naming every resolved value and where it came from. That log line is currently the only way to confirm an edit took effect. Writing `source` into `helios_runs.model_metadata`, and a guarded `GET /config` route, are both natural follow-ups and both out of scope here — the route reveals which models are in use, so it needs a guard, and a guard needs a secret.

Across engines, each engine gets **its own KV namespace**, bound as `CONFIG`, using the same flat key names. The binding name is deliberately unprefixed so every engine's worker code is identical; the namespaces are distinguished by their dashboard titles instead, `HELIOS_CONFIG` for this one. Two alternatives were rejected: one shared namespace with `helios:`/`iris:` key prefixes, which would put every engine's config on one dashboard page at the cost of any isolation between them and a prefix constant in every engine; and one JSON blob per engine, which reads and edits in one shot but turns a single dashboard typo into a total config failure rather than one bad field.

Each engine gets exactly **one** namespace, with no `preview_id`. Cloudflare's preview/production split is the default for KV bindings and was tried here first, but it means the same key exists in two stores that look identical in the dashboard, and a value edited in one silently does nothing in the other — the failure is invisible and costs more time than the isolation saves. Config values are not user data: the blast radius of a wrong one is a warning line and a fallback, which does not justify a second store. The accepted consequence is that there is no staging tier for config. Anything read from KV is read from the same store that production reads, so a wrong value in the dashboard is wrong everywhere at once, and `wrangler kv key put` from a terminal writes production.

Local development therefore does **not** read that namespace by default. `wrangler dev` uses Miniflare's simulated KV in `.wrangler/state/`, which is empty on a fresh clone, so every value falls back to its var and the log line reads `(var)` four times. That is the correct state, not a broken one. When local dev genuinely needs the real values, the `remote` flag on the KV binding in `wrangler.jsonc` sends that one binding to the live namespace while the Durable Object, D1 and R2 stay local. It is committed commented-out and flipped for a session rather than left on, because leaving it on makes every local run depend on the network and on an authenticated wrangler, and makes a stray `kv key put` a production edit.

Two existing defects close as a side effect. `planner.ts` did `Number(env.MAX_RETRIES)`, and had that var ever been absent or non-numeric the result would have been `NaN`, which the destructuring default in `getTextualModelOutput` does not catch — `attempt <= NaN` is false, so the helper would throw "failed after NaN attempt(s)" without ever calling the model. And `pipeline.ts` recorded `{ model: env.PLANNER_MODEL }` on the text row while the planner call read the same var separately; both now read one resolved value, so the audit row cannot disagree with the call that produced it.
