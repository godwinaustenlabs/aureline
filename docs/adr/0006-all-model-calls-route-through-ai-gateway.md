# All Workers AI calls route through AI Gateway, configured per call rather than per binding

Until now every model call went straight to Workers AI through the `ai` binding. That was never a decision — `ai.run(model, inputs)` is the shape every Cloudflare example uses, and nobody passed the optional third argument. Three concrete gaps follow from it. `helios_runs` has a `cost_usd` column per modality row (ADR-0001) and Workers AI returns token counts at best, never dollars, so there is no source for that column. Worker observability logs our own code, not the model's request and response bodies, which is why establishing the gpt-oss-120b response envelope cost real debugging time. And there is no response cache, so every repeated call bills the account — against a standing constraint not to exhaust it.

Decision: all Workers AI calls made through `packages/shared-utils` pass a gateway configuration as `ai.run`'s third argument — `ai.run(model, inputs, { gateway: { id } })`. The id comes from `AI_GATEWAY_ID` in `apps/agent-helios/wrangler.jsonc` `vars`, matching how `PLANNER_MODEL` and `IMAGE_MODEL` are already supplied. The gateway is created manually in the Cloudflare dashboard (AI > AI Gateway); there is no `wrangler` command for it, and the id is the gateway's name, not a UUID.

Rejected alternative: `env.AI.gateway(id)`, the universal-endpoint style. That form is for reaching non-Workers-AI providers through a Gateway and needs provider credentials in the Worker. We call Workers AI models exclusively, so the per-call option keeps the existing binding, adds no secret, and leaves each call site free to opt out.

Retry stays where it already is. `getTextualModelOutput` retries schema drift, which is a class of failure the Gateway cannot recognise — a syntactically fine 200 response that fails validation. `GatewayOptions.retries` is deliberately left unset so there is exactly one retry layer and the attempt count stays truthful for the `helios_runs` audit row. Two retry layers would mean a "single attempt" could be several billed calls.

Caching is asymmetric on purpose. `getImageModelOutput` sets a one-hour `cacheTtl` by default: the same parameters should render the same pattern, and the image call is the expensive one. `getTextualModelOutput` sets none, because a cached planner response would be replayed identically on every retry, defeating the retry loop, and because a stale planner result during development looks exactly like a working one. Callers can override either with an explicit `cacheTtl` or `skipCache`. Note that the cache key covers the model inputs, so varying `seed` produces a fresh generation.

An absent or empty `AI_GATEWAY_ID` degrades to a direct Workers AI call rather than throwing. Unit tests and any local run against an account with no gateway provisioned must keep working; a missing observability layer is not a reason to fail a request.

Consequence: `cost_usd` now has a source, and it is cheaper than expected. A probe against `@cf/meta/llama-3.2-1b-instruct` through the `helios` gateway returned `usage.neurons` directly in the response body alongside the token counts — no Gateway REST API call and no account token required. Cloudflare bills Workers AI in neurons at $0.011 per 1,000 (10,000/day free), so `cost_usd = neurons / 1000 * 0.011`. Ticket 03 can populate the column from the model response.

Two caveats on that. The rate is a published price that will drift, so it belongs in config rather than hard-coded in a helper. And the probe only covered a text model — **needs confirmation** whether Flux Schnell returns a `usage` block at all, since image models are billed per-image on some tiers. Until that is checked, the image row's `cost_usd` may still be `null`.

`GatewayConfig.metadata` is the natural carrier for `p_invoc_id`, which lets a Gateway log row be joined back to a `helios_runs` row. Nothing mints one at this layer yet, so ticket 05 should pass it. Note the binding also exposes `env.AI.aiGatewayLogId` after each call — non-null confirms the request was routed through the Gateway, and it is the id to search for in the dashboard log. That is the cheapest way to verify gateway configuration without reading the dashboard first.
