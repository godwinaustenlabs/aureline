# A HeliosAgent Durable Object instance is scoped to a session/project, not to a pipeline invocation

The architecture docs decided that each engine gets its own Durable Object *class*, Worker, D1 database, and R2 bucket — that is deployment and blast-radius isolation, and it is settled. What they never decided is how many *instances* of that class exist at runtime. A DO class is a template; instances are addressed by name, and "each engine has its own DO" is equally true of one instance, one per user, or one per request. That ambiguity surfaced while building Ticket 01, because `p_invoc_id` has to come from somewhere and the spec's retention rule quietly assumes an answer.

We considered a **singleton** instance (every invocation from every user routes to one object, forever). Rejected: it is a platform-wide bottleneck living in a single colo on a single thread, its SQLite grows without bound, and it inverts the isolation the architecture exists to provide — the DO becomes a shared resource rather than an isolating one, with no path to multi-tenancy that isn't a rewrite of the addressing model.

We also considered **one instance per pipeline invocation**, which is superficially attractive: perfect isolation, no contention, and `p_invoc_id` falls out of the DO's own identity for free. Rejected for two reasons. First, it uses a Durable Object as a glorified function call — a DO's value is durable state *across* requests, and a single-request DO exercises only the "hold storage for a crashed run" slice of that. Second, DO instances are created implicitly and cannot be enumerated from inside the Worker runtime (only via an admin REST endpoint listing objects with stored data), so a run that fails after writing and before cleanup leaves storage that nothing in the system knows about — D1 would become the de facto index of our own DO storage. It also makes the spec's 5-run retention rule structurally dead: such a DO holds at most two rows (`text` and `image`), so a "prune once more than 5 completed runs exist" check could never fire.

**Decision:** a `HeliosAgent` instance is scoped to a session/project. The instance name is a caller-supplied scope key (`session_id`), defaulting to `"default"` in Sprint 1 while the playground is the only caller. `p_invoc_id` is a `crypto.randomUUID()` minted per invocation in `services/pipeline.ts` — it is not any Durable Object identifier.

This is the model the sprint spec was implicitly written against: "retain the 5 most recent runs, prune older, never prune failures" is a user-history policy, coherent only when a DO accumulates a bounded stream of runs belonging to someone. So User Story 8 and Ticket 07 stand exactly as written, with no amendment.

The scope key is just a parameter, which is why this costs nothing now and saves a rewrite later. Sprint 1 behaves identically to a singleton, but the shape is already correct: when Athena arrives holding a design session, it passes that session id to Helios, Iris, and Atlas alike, and each engine's DO accumulates that session's history without any change to the addressing model. The trade-off accepted is that two concurrent invocations in the same session share an isolate — since a pipeline invocation is almost entirely awaiting network I/O from Workers AI, they interleave rather than block, and the contention is per-session rather than global.

Like the `helios_` table prefix (ADR-0003), this applies to every future engine built from the `agent-helios` template, not to Helios alone.
