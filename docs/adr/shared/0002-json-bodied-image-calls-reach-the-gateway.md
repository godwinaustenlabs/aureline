# A JSON-bodied inpainting model is how Iris's image call reaches AI Gateway

ADR-SHARED-0001 established that `getImageToImageOutput` cannot route through AI Gateway and never will: `@cf/black-forest-labs/flux-2-klein-9b` requires `multipart.body` to be a `ReadableStream`, and AI Gateway refuses a `ReadableStream` by name. The only body type the model accepts is the only body type the gateway refuses. That ADR is still correct, and nothing here retracts it.

What it left standing was a consequence nobody was happy with: Iris's image row carried `cost_usd: null` on every run and left no gateway log row, so the expensive half of every invocation was unaudited. ADR-SHARED-0001 recorded that null as a decision rather than an accident, which was honest, but it was still the wrong answer to be stuck with.

A probe on 2026-08-31 found the way out. It is not a fix to the multipart path — that path is unfixable from our side — but a different model with a different request shape. `@cf/runwayml/stable-diffusion-v1-5-inpainting` takes a plain JSON body, and a plain JSON body routes through the `iris` gateway without complaint (verified end to end, `aiGatewayLogId` `01M1C43NMHZKZSP1GHNHDDW9KX`).

Everything else on the account was ruled out first, and the rejections are worth keeping so nobody re-walks them: `sdxl-base` and `xl-lightning` carry no image tensor and answer `3030`; `dreamshaper-8-lcm` wants an `image` of shape `[1]`, which nothing produces; and `stable-diffusion-v1-5-img2img` answers `5018` — it is not on the account at all.

Decision: **Iris runs the inpainting model on a JSON body by default, and reaches AI Gateway.** `cost_usd` on the image row is a real number again, the run appears in the gateway dashboard carrying its `pipeline_id`, and cost reporting stops having a hole in it.

**The price is real, and is being paid deliberately.** The inpainting model returns 512x512 against flux-2-klein's 1024x1024, and side by side its recolour is visibly weaker — the pattern survives, the colour is less committed. This was reviewed against real output from both models before the decision, not assumed. The judgement is that a working gateway, a real per-run cost and an auditable log row are worth more than the resolution, and that a run nobody can price is a worse artefact than a run that is smaller.

Decision: **which transport is used is an explicit config field, never inferred from the model id.** `ImageModelConfig.transport` is `"multipart" | "json"`, required, with no default, and it is what selects which helper runs. Inferring it from the model string was considered and rejected: an unlisted id would have to fall back to a guess, and a guess here sends the wrong body shape to a billed model and fails the run. Requiring the field means a KV value that omits it is invalid and falls back to the reviewed vars *with a warning*, which is the behaviour every other invalid config value already has. It also means a bare model id is no longer a sufficient `image_model` — a deliberate cost, paid once, in exchange for never guessing.

Consequence: **both models stay reachable, and switching between them is a KV edit rather than a deploy.** `{ "model": "@cf/black-forest-labs/flux-2-klein-9b", "transport": "multipart" }` puts Iris back on the better images and the null cost, with no code change. That is the reason the multipart path is kept rather than deleted, and the reason ADR-SHARED-0001 remains live documentation rather than history.

**The rule that keeps the two apart: a gateway id is passed on the JSON path and never on the multipart path.** This is not a style preference. `getImageToImageOutput` throws outright when given a gateway id, before anything bills, precisely so that this mistake is loud — so passing one on the multipart branch fails every run. The two calls live in separate functions in `colorizer.ts` so the pairing is structural rather than a comment somebody edits past, and `colorizer.test.ts` asserts both halves: that the JSON branch passes an id, and that the multipart branch passes none *even when `AI_GATEWAY_ID` is set*.

Decision: **the code lives in a new helper, `getInpaintingOutput`, and `getImageToImageOutput` is not touched.** The two have nothing in common below the signature — different body, different response shape, different gateway answer — so a `transport` branch inside one function would have been two functions sharing a name. It also matters that `atlas-07` forbids modifying `packages/shared-utils` while Atlas is mid-sprint; a purely additive change is the mildest form that constraint can be broken in, and it still has to be raised with the Atlas manager rather than assumed.

One detail of the request shape, because it is not guessable and the near misses all look reasonable: `image`, `mask` and `mask_image` each take a **raw array of byte values**. `image_b64` is decoded by the binding to a tensor of the wrong shape. `image` as a bare base64 string is rejected with `5006: Type mismatch of '/image', 'array' not in 'string'`. And `mask` and `mask_image` carry the same bytes deliberately — sending one without the other returns `3030: model input not valid`, naming the absent tensor.

**Why the mask is white.** Inpainting repaints only where the mask is white and leaves the rest alone, so a mask that is white everywhere means "repaint the whole thing" — which is what a recolour is. An earlier probe passed the motif's own bytes as the mask, which means "repaint roughly where the pattern already is", and came back barely changed. `whiteMaskPng` generates it, sized to the motif so the model is not asked to reconcile two shapes, falling back to the model's native 512x512 when the motif cannot be measured.

Consequence: **PNG now travels through the whole stack, truthfully.** The inpainting model returns PNG where flux-2-klein returns JPEG, so `readImageDimensions` dispatches on the magic bytes rather than assuming, and `saveColoredImage` takes the R2 key's extension from the content type — `iris/{pipeline_id}.png` on a JSON run, `.jpg` on a multipart one. Both throw on a format they do not recognise rather than defaulting to one: these numbers and this key are reported as fact, and a plausible wrong answer outlives the run that produced it. Downstream consumers receive the full image URL rather than rebuilding the key, so the varying extension costs them nothing.

Consequence: the JSON body is large. A 1024x1024 JPEG serialized as an array of byte values is roughly 2-3 MB of request body, and the mask adds to it. The verified run did exactly this and it worked. There is still no resize step, for the reasons already recorded in `colorizer.ts`: a Worker has no `sharp`, and the Images binding needs a human to enable it on the account.

What would reverse the model choice: AI Gateway supporting `ReadableStream`, which is the same condition ADR-SHARED-0001 names. On that day flux-2-klein can be both the better image and the audited one, `allowGatewayMultipart` comes off its guard, and the transport field becomes a detail rather than a trade. Until then it is a trade, and this is the side of it we chose.
