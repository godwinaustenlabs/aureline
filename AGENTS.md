Conventions for anyone writing code in this repo. Read this before you touch anything.
Where a rule points at a doc, read the doc, this file does not repeat what `docs/` already explains.

## 1. What this repo is

Aureline turns a textile design concept into a production-ready design. It does that with **engines**: small, independently deployable Cloudflare Workers that each own one part of the problem. `agent-helios` (patterns) and `agent-iris` (colour) exist today; Atlas and others follow.

It is a plain npm-workspaces monorepo — `apps/*` for the deployable engines, `packages/*` for shared code. No Turborepo, no shared base tsconfig. Each workspace carries its own `tsconfig.json`.

## 2. Where new files go

Every engine follows the same layout. `apps/agent-helios` is the template; copy its shape, not just its code.

| Path | What belongs there |
|---|---|
| `src/index.ts` | The Worker entry point: routing, CORS, picking the Durable Object |
| `src/agent.ts` | The Durable Object class. Request validation and route dispatch |
| `src/config.ts` | **The only place runtime config is read.** Nothing else reads KV or `env` for config |
| `src/db/schema.ts` | Drizzle table definitions |
| `src/db/client.ts` | Database client factories |
| `src/repository/` | **Every database statement in the codebase.** One function per thing the pipeline records |
| `src/services/` | Pipeline orchestration, model calls, cost accounting |
| `src/prompts/` | Prompt construction, nothing else |
| `src/utils.ts` | Genuinely generic helpers |

Rules:

- **A file that talks to the database goes in `repository/`**, even if it holds one function. The split exists so services say *what happened* and repositories own *how it is stored*.
- **No new top-level folders** without saying why in the PR. 
- Migrations live in two different places on purpose:
  - **DO-local SQLite** → `apps/<engine>/drizzle/` — generated by `npm run db:generate`
  - **D1** → `infrastructure/d1/migrations/<engine>` — generated by `npm run db:generate:d1`

## 3. Identifiers: session, design session, pipeline

Three different ids that all look like UUIDs and mean completely different things.

**`session_id` — which Durable Object serves this request.** That is all it does. It is a routing key (ADR-0005). One session is one user working on one project, and it outlives many runs. It is *not* an identity for any piece of work, and nothing should ever treat it as one.

**The design session id — one design, across every engine.** Minted once at the very start and carried forward unchanged through Helios → Iris → Atlas. This is the id that answers "show me everything that went into this design." Every engine receives it, stores it, and passes it on untouched. An engine that mints its own here has broken the chain for everything downstream.

**The pipeline id — one run of one engine.** Fresh for every invocation. If a user re-runs Iris on the same design, that re-run gets a new pipeline id while the design session id stays the same — which is exactly how "which attempt is the latest" stays answerable. Per ADR-0001 an invocation writes two rows (one `text`, one `image`) that share this id.

You need both. The design session id alone cannot tell two re-runs apart. The pipeline id alone cannot connect Iris's work to the Helios pattern it coloured.

> **Naming as it stands today:** Iris uses `design_session_id` and `pipeline_id` throughout —
> the wire contract, the `iris_runs` columns, and the code.

## 4. TypeScript

**Never write `as never`.** Not in tests, not in source, not "just to get this compiling." It does not adapt a value to a type — it switches off checking at that call site entirely. This repo has ~92 of them and they are why a real schema mismatch shipped: the tests were green the whole time because they had stopped looking.

The rule underneath it: **a type error is information about your data. Fix the data, not the error.** If `startImageRun` will not accept your object, the object is wrong, or the function signature is wrong. Either way, casting hides which.

Also banned, for the same reason: `any`, `@ts-ignore`, `@ts-expect-error` without an explanation, and `as unknown as T`.

The one legitimate escape is a genuinely untyped third-party boundary. When you need one, put the reason on the line above it:

```ts
// The agents SDK types storage as `unknown`; the runtime guarantees DurableObjectStorage.
const storage = this.ctx.storage as DurableObjectStorage;
```

If you cannot write that comment honestly, you do not have the exception.

## 5. Tests

**Build complete, real objects.** Not a partial plus a cast. If a test needs an `iris_runs` row, it builds a whole valid one. That is the entire point — the test is checking the shape, and a cast is a way of not checking the shape.

```ts
// No.
await startImageRun(db as never, "run-a", { primary_color: "gold" } as never, {});

// Yes.
await insertRow(db, { pInvocId: "run-a", modality: "image", status: "running" });
```

Other rules:

- **A test that would still pass with the function deleted is not a test.** Assert on the thing that changed, not on the absence of a throw.
- **Tests never call a model and never touch the network.** Fake the `AI` binding. CI has no Cloudflare credentials and must never need any — a test that needs a secret is a test that is wrong.
- Every repository function gets a test. Every schema boundary gets a test proving a wrong shape is *rejected*, not just that a right one is accepted.
- Run them with `npm test` (which is `vitest run`). They must pass before you open a PR.

## 6. Function signatures mirror their schema

When a function's parameters come from a schema, **list them in the same order the schema lists them.** Same order in the request body, same order in the table definition, same order in the signature. A reader checking a call site should be able to check it by looking, not by counting.

**Once a function takes more than three parameters of the same primitive type, take a single object instead.**

```ts
// Four adjacent strings. Swap any two and it compiles, runs, and corrupts a row.
startImageRun(db, pInvocId, sourcePInvocId, userPrompt, motifRef, params, metadata);

// Swap any two and it is a compile error.
startImageRun(db, { pInvocId, sourcePInvocId, userPrompt, motifRef, params, metadata });
```

This is not style. In `resume.ts` a swap here corrupts the image row, the code then fails to find `status` on it, and the pipeline regenerates the image forever — unbounded model spend, with nothing written down to show for it.

## 7. Defensive reads

The compile-time half is §6. This is the runtime half.

**When you read a row back and branch on one of its fields, handle the missing case explicitly.** Optional chaining that quietly falls through is the bug, not the fix:

```ts
// apps/agent-helios/src/services/resume.ts:62-68 — both guards use `?.`, so a
// row that is missing or corrupted matches neither and execution continues
// straight into generating another image.
const imageRow = rows.find((row) => row.modality === "image");
if (imageRow?.status === "completed") return refuse(...);
if (imageRow?.status === "running")   return refuse(...);
```

What to do instead: check for the malformed row *first*, and fail loudly rather than falling through. `undefined` and "present but not the value I expected" are two different situations and usually want two different answers.

**Anything that can trigger a repeated model call needs a bounded attempt count and a guard that trips on a malformed row.** Money is the reason this section exists. A loop that costs nothing is a bug; a loop that calls an image model is an invoice.

## 8. Database and migrations

Read [docs/database.md](docs/database.md) for how the two stores divide the work. The rules on top of it:

- **One invocation writes two rows**, one per modality, sharing a pipeline id (ADR-0001). Never one, never three.
- **Migrations are generated. Never hand-edit one.** Change `src/db/schema.ts` and re-run `npm run db:generate` (DO-local) or `npm run db:generate:d1` (D1). A hand-edited migration and its snapshot disagree, and the next generated migration is then built on a lie.
- `src/repository/test-db.ts` creates its table with hand-written SQL that mirrors `schema.ts`. **If you change the schema, change that too** — nothing enforces the match, and if it drifts the tests pass against a table that no longer exists in production.
- **Never hand-merge or hand-edit `package-lock.json`.** On a conflict: delete it, reinstall, commit the fresh one. Lockfiles are generated artifacts; a person merging one produces a tree that resolves on nobody's machine.
- To add a dependency: `npm install --package-lock-only`, never a bare `npm i`.

## 9. Secrets and runtime config

- **Secrets go in `wrangler secret put` (deployed) and `.dev.vars` (local). Never in `wrangler.jsonc` `vars`** — that file is committed, so a secret in it is a published secret. `.dev.vars` is never committed.
- **`ALLOWED_ORIGINS` is never `*`.** List the origins.
- **Runtime config is read only through `config.ts`**, once per request, never at module scope and never at wake-up (ADR-0008). Two reads straddling a KV edit produce one invocation that is half old model and half new.
- **After editing anything in `wrangler.jsonc`, re-run `npm run cf-typegen`.** `wrangler types` produces literal types, so a stale `worker-configuration.d.ts` typechecks against values that are no longer real. There is already one committed in this repo with a stale `ALLOWED_ORIGINS` — that is the mistake this rule prevents.
- Reach local KV through the `kv:get` / `kv:put` scripts, not bare `wrangler`. Run from the repo root, bare `wrangler` finds no `wrangler.jsonc`, silently leaves KV untouched, and your next request is a normal billed run instead of the failure you were trying to force.

## 10. Git and pull requests

- **Branch naming: `<type>/<ticket>-<short-name>-<YourName>`** — e.g. `feature/iris-01-shared-contract-and-schemas-MaazBinAsif`, `chore/iris-ticket-corrections-MaazBinAsif`. Types in use: `feature`, `fix`, `chore`, `docs`.
- **Cut from the engine's integration branch** (`dev-iris`, `dev-atlas`), never from `dev` directly. Two squads work at once and `dev` should only ever receive a working set.
- **Keep changes under roughly 400 lines.** A change too big to review carefully gets reviewed carelessly instead.
- **Tick the ticket's checkboxes in the same change that does the work.** Left for later means not done.
- **Never run a deploy.** Deploys are manual and a human does them.

## 11. Commands

From the repo root:

| Command | What it does |
|---|---|
| `npm install` | Install everything. Node 24+ required — the repository tests use `node:sqlite` |
| `npm test` | Every workspace's tests. No model calls, free |

From inside an app (`apps/agent-iris`, `apps/agent-helios`):

| Command | What it does |
|---|---|
| `npx tsc --noEmit` | Typecheck. **Must run from inside the app**, not the root — the apps use `moduleResolution: node`, which only resolves from their own directory |
| `npm run dev` | Local dev server on `:8787` |
| `npm run cf-typegen` | Regenerate `worker-configuration.d.ts` after a binding or `var` change |
| `npm run db:generate` | Generate the DO-local migration from `schema.ts` |
| `npm run db:generate:d1` | Generate the D1 migration from `schema.ts` |
| `npm run kv:get` / `kv:put` | Read and write local KV config |

### Never run

- **Anything that makes a real model call.** `wrangler dev` bills your real Cloudflare account — the `AI` binding has no local simulator, so `POST /generate` on localhost costs money exactly as in production. Never put one in a loop.
- **`wrangler deploy`.** See §10.
- **Creating or deleting a Cloudflare resource** — D1 databases, R2 buckets, KV namespaces, AI Gateways. A human does these and hands back the ids.

### One trap worth its own line

**Stop the dev server before running any wrangler command against local D1 or KV.** The dev server holds those files open, the command appears to do nothing at all, and you will lose an afternoon to it.
